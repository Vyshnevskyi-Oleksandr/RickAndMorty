## Як запустити

Цей проєкт використовує нативні модулі (зокрема `react-native-mmkv` для дуже швидкого локального сховища), що означає, що для нього потрібен кастомний Development Build, а не стандартний додаток Expo Go.

1. Встановіть залежності:
   ```bash
   npm install
   ```
2. Запустіть development build на емуляторі Android або підключеному пристрої:
   ```bash
   npx expo run:android
   ```
   *(Для iOS виконайте `npx expo run:ios` на Mac зі встановленим Xcode).*

3. Щоб запустити тести:
   ```bash
   npm test
   ```

## Expo чи CLI

Я обрав **Expo (з Continuous Native Generation / Prebuild)** замість "голого" React Native CLI. 

Станом на 2026 рік Expo став стандартом де-факто для більшості нових проектів (його офіційно рекомендує команда React Native). Використовуючи Expo Development Builds, я отримую найкраще з обох світів: легкий процес розробки та зручний роутинг Expo (через `expo-router`), зберігаючи при цьому повний доступ до будь-яких нативних бібліотек (як-от `react-native-mmkv` чи `reanimated`). Папки `ios` та `android` тепер розглядаються як артефакти збірки (build artifacts), що неймовірно спрощує оновлення та підтримку коду.


## Що б я зробив, маючи ще кілька годин

1. Я б додав вкладку "улюблені" для виводу героїв, які вже додані в улюблені.
2. Я б додав плавні анімації переходу спільних елементів (Shared Element Transitions) за допомогою Reanimated при переході зі списку персонажів до екрану деталей, щоб додаток відчувався ще більш преміальним.
3. Можна було б зробити можливість використання додатку офлайн.
4. Я б налаштував Maestro або Detox для покриття критичних шляхів користувача (пошук, пагінація та додавання персонажів до улюблених).

## Випуск у Продакшн (App Store / Google Play)

Щоб випустити цей додаток в App Store та Google Play, я б активно використовував **EAS (Expo Application Services)**:

1. Налаштував би ідентифікатор додатка, версіювання та іконки в `app.json`.
2. Виконав би `eas build --profile production --platform all`, щоб згенерувати `.aab` (Android) та `.ipa` (iOS) бінарні файли у хмарі. Це безпечно вирішує всі питання з керуванням ключами (keystore) та профілями доступу (provisioning profiles).
3. Використав би `eas submit`, щоб надіслати бінарні файли безпосередньо в Google Play Console та Apple App Store Connect / TestFlight.
4. Я б інтегрував ці EAS-команди у робочий процес GitHub Actions для автоматичної збірки та публікації релізів при злитті коду в гілку `main`.

## Робота з платформозалежними / нативними функціями

Коли мені потрібні нативні можливості (наприклад, deep linking, біометрія або доступ до камери), мій підхід за замовчуванням — використовувати надійну екосистему модулів Expo (наприклад, `expo-local-authentication`). На відмуну від CLI, Expo надає зручний спосіб роботи з нативними можливостями.

Однак, якщо мені потрібна дуже специфічна нативна функція, яка не покривається існуючими пакетами, я б зробив наступне:
- **Для нативної конфігурації (дозволи, зміни в маніфесті):** Я ніколи не редагую папки `ios` або `android` вручну. Натомість я пишу **Config Plugin** (плагін конфігурації) в `app.json`, щоб втрутитися в процес пребілду і автоматично додати необхідні зміни в `AndroidManifest.xml` або `Info.plist`.
- **Для кастомного нативного коду:** Я б створив локальний **Expo Module**. Модулі Expo використовують сучасний API на Swift/Kotlin, який неймовірно легко зв'язується з TypeScript. Це дозволяє мені писати власну нативну логіку без "ejecting" (виходу з екосистеми) та без порушення робочого процесу Continuous Native Generation.
